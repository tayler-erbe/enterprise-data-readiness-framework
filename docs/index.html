TAYLER ERBE / PROPOSAL · DATA READINESS BEFORE A MIGRATION

Is this data ready for AI? Find out before you move it.

A move to a new ERP or a cloud data platform carries hundreds of warehouse tables with it. Some are well defined and ready. Others have codes nobody can decode, columns nobody has described, or values that don't match their definitions. This review reads what the data dictionary already says about each table, looks at a small snapshot of the data, and reports which tables are ready, which are not, and how sure it is.

Short answer: give an AI model the table and column definitions plus about twenty sample rows. Ask it, column by column, whether it can tell what the data means and whether the data matches what is written about it. Score each table for readiness, certainty and value, then fix the most valuable tables first.

THE REVIEW

Context first,
then a look at the data.

A data dictionary or catalog already works as a semantic layer: it holds table definitions, column definitions, code meanings, usage rules and data quality advisories. The review puts that context next to a small sample of real values, and asks whether the two agree.

  1. Read the dictionary
  2. Take a snapshot
  3. Review each column
  4. Score the table
  5. Rank by value
  6. Fix with the owners
Deterministic codeAI modelPeople

  1. Read the dictionary

    Pull each table's definition, its columns, data types, keys, code tables, usage rules and advisories. Code also checks the basics: missing descriptions, placeholders, broken links.

  2. Take a small snapshot

    Read the header and about twenty rows. Restricted columns, such as identifiers and protected attributes, are masked or summarised before anything reaches a model.

  3. Review column by column

    For each column the model answers fixed questions: what this column means, whether the values match the definition, whether the codes can be decoded, and what it is unsure about.

  4. Score the table

    Code rolls the column verdicts into three scores: how ready the table is, what share of it the model is certain about, and how much the data is worth building on.

  5. Rank by value

    Tables that matter most and are least ready rise to the top. Ready tables are cleared to move. Low-value tables wait.

  6. Fix with the owners

    Each table gets a short worklist for its system owner: the exact columns to define, codes to document and values to confirm. The review never edits the data itself.

!

A table list alone is not enough.

A first pass on a table-list export found that table names and descriptions can't place any table above "described". Telling whether data is usable takes column definitions and a look at real values, which is why the snapshot is part of the design.

What the model sees ↓

WHAT THE MODEL SEES

Six inputs,
not a full copy.

The model doesn't need much data. It needs the meaning that people already wrote down, and enough rows to check that meaning against reality.

TABLE DEFINITION

What one row is

The table's description, its keys, and any statement of grain such as "one row per employee per job change".

From the data dictionary

If the grain isn't written down, the model proposes one from the keys and marks it unconfirmed.

COLUMN DEFINITIONS

What each column means

Name, data type, description and whether it is part of a key.

From the data dictionary

Copied descriptions, where two columns share the same text, are flagged.

CODES AND LOOKUPS

What the codes stand for

Code tables and value lists that turn "R1" into a reason someone can read.

From the data dictionary

A code column with no lookup is uncertain until someone names its source.

RULES AND ADVISORIES

When not to use it

Valid date ranges, known gaps, exclusions and data quality advisories.

From the data dictionary

Rules buried in long descriptions are pulled out and listed separately.

DATA SNAPSHOT

What the values look like

The header and about twenty rows: formats, blanks, codes in use, sentinel dates such as 12/31/9999.

Small sample · masked

A sample shows formats, not frequencies. It can't prove a rare problem is absent.

KNOWN QUESTIONS

What people need from it

The questions the business already asks, such as turnover, promotion and pay equity, used to judge value.

From the data owners

Value is judged against stated needs, never guessed from the table name alone.

One column
at a time.

For every column, the model says what it understood, what the sample shows, and whether the two agree. Anything it had to guess is labelled as a guess.

Each verdict comes with the evidence behind it: the definition, the sample values and the model's reasoning. People confirm or correct verdicts; the model never decides alone that a table is ready.

THE SCORES

Three questions
for every table.

Readiness says whether the table can move as it is. Certainty says how much of that judgement rests on clear evidence. Value says whether the table is worth the effort of fixing.

READINESS

Can it move as it is?

Ready, ready with notes, or not ready. A table that is not ready gets the share of columns holding it back, such as "not ready by 21%", and the list of those columns.

CERTAINTY

How sure is the review?

The share of columns the model understood from clear evidence, against those it had to infer or flag. A high readiness score with low certainty means "probably fine, check first".

VALUE

Is it worth building on?

How well the table serves known questions, whether it can be cleaned or pre-processed, and which derived features it supports. Some data is interesting but has little use.

ASKED OF EVERY COLUMN

Meaning

  • What does this column hold?
  • Does the definition match the values?
  • Can its codes be decoded?
  • Is it part of a key or a join?
ASKED OF EVERY COLUMN

Doubt

  • What did the model have to guess?
  • Are there blanks, sentinels or mixed formats?
  • Do two columns repeat each other?
  • Does it hold restricted information?
ASKED OF EVERY TABLE

Use

  • Which known questions does it answer?
  • Can it be pre-processed into something clean?
  • Which derived features can it support?
  • Would an AI tool read it correctly today?

tables first.

Hundreds of tables can't all be fixed before a migration. Crossing readiness with value shows where owners' time pays off, and which tables can move now.

SCOPE

It evaluates.
It doesn't repair.

The review tells owners what is wrong and how sure it is. Fixing definitions, codes and values stays with the people who own the data.

What it does

Reads the semantic layerUses the definitions, codes and rules already in the data dictionary.
Checks a small snapshotAbout twenty rows per table, masked where needed.
Scores every columnReady, uncertain or concern, each with its reason.
Ranks tablesBy readiness and value, so the work list starts where it matters.

What it doesn't do

Edit data or definitionsNothing in the source system or the dictionary is changed.
Profile whole tablesA sample shows formats and codes, not how often a problem occurs.
Decide aloneEvery "ready" is a proposal until a data owner confirms it.
Send bulk data outThe model sees definitions and a masked sample, run on approved infrastructure.

Next: a pilot
on one business area.

Pick an area with high-value questions and hard definitions, such as HR or finance. That makes a good first test.

01 / GATHER

Dictionary context

Collect table and column definitions for a pilot set of tables, starting with the ones the business asks about most.

02 / AGREE

The rubric

Settle with data stewards what "ready", "uncertain" and "high value" mean, and which columns must be masked.

03 / RUN

The column review

Run the model on definitions plus masked snapshots, and have owners check a share of its verdicts by hand.

04 / RANK

The work list

Publish a ranked list of tables to fix before the migration, with each owner's columns, codes and rules to settle.

Built on what exists. A deterministic scorer already reads data dictionary exports and places each table on a five-level scale from undocumented to AI-ready. The AI column review adds the judgement that code alone can't make.
