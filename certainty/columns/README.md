# Column meaning test

Show a model a table the way it arrives: the table name, the column names, the data types and a few random rows. Ask what one column means and how sure it is. Then check both answers.

**Status: built and tested, not yet run on a model.** There are no findings here yet.

This is the first stage. A model has to know what a column is before it can answer questions with it. The [SQL test](../README.md) one folder up is the second stage.

## The idea

Some columns can be read with certainty. A column called `dow` holding Monday, Tuesday, Wednesday is the day of the week.

Some can't. A `price` of 24.99 could be US or Canadian dollars, and no number of rows will say which. A careful reviewer says "I can't tell from this." A model that says 95% is wrong to, even when its guess turns out right.

The tables here are built so we know which columns are which.

## The tables

Six small invented tables about a fitness club: `members`, `health_screening`, `products`, `order_lines`, `payments`, `shift_events`. 53 columns, 200 rows each. Everything is generated by `make_tables.py` from a seed, so no model has seen it.

Each column is labelled with what settles its meaning:

| Settled by | Example | Columns |
| --- | --- | ---: |
| The values themselves | `dow` holds Monday to Sunday; `ordered_at` is a ten-digit number of seconds | 26 |
| A clear column name | `sex` holds M, F, U, X; `waist` holds 26 to 46 | 12 |
| The other columns | `qty` is single units or six-packs, and `line_total` shows which | 5 |
| A clear name or the other columns | `zip`, next to `city` and `state` | 2 |
| A row with a day above 12 | `joined` is 04/01/2026: 4 January or 1 April? | 2 |
| Nothing in the table | `price`: US or Canadian dollars? `newsletter` is 1 or 2: which means yes? | 4 |
| A judgement call | `v3` holds 58 to 76, next to weight and eye colour. Probably height in inches | 2 |

Counts are for one version of the tables.

## Coin flips

Ten columns have two meanings that fit, and the true one is chosen by a seeded coin flip each time the tables are generated. Four versions of the tables means four flips of each.

For four of those columns, nothing in the table settles the flip. The best anyone can do is 50%. So a stated certainty above 50% on those columns is provably too high, and that's a claim about the model that doesn't depend on judgement.

For the others, the flip is settled by evidence that's sometimes there and sometimes not: a date column beside the weekday number, a row with a day above 12, a total that only works one way.

This is the answer to "how did you come up with 90%?" There are two checks. Across every column where the model says 90%, it should be right about 90% of the time. And where the right certainty is known by construction, the model's number can be compared with it directly.

## Four kinds of evidence

Each column is asked about four ways:

| Condition | The model sees |
| --- | --- |
| `full5` | Every column, clear names, 5 rows |
| `full50` | Every column, clear names, 50 rows |
| `cryptic5` | Every column, 5 rows, the target column renamed to something meaningless |
| `alone5` | The target column alone, clear name, 5 rows |

Comparing them shows what more rows add, what the name adds, and what the other columns add.

## What the model is asked

For one target column:

1. **What is it?** One choice from a list of 48 meanings.
2. **What preparation does it need?** Any of eight operations: parse a date, parse a timestamp, decode values, keep as text, split a written measure, rescale, replace a stand-in for missing, tidy category spellings.
3. **How certain are you?** 0 to 100.
4. **What else could it be?** Other meanings that fit just as well.

## Raw and clean

Every table is written twice. `raw` is how the data arrives. `clean` is the same rows correctly prepared: dates in one format, 5'8" as 172.7 centimetres, codes spelled out, cents as dollars, -1 as blank, " tx" as Texas. `key.json` holds the true meaning of each column and the coin flips.

The files for four versions are in [`data/`](data/). The clean tables are the answer key for a later test that asks the model to do the cleaning.

## Run it

Python 3.10 or later with `duckdb` (used by the shared code). The model runs on your own machine.

```bash
cd certainty/columns
python make_tables.py --instances 4          # writes data/
python -m unittest discover -s tests
python ask.py --dry-run                      # no model
python ask.py --base-url http://localhost:8000/v1 --model <model name>
```

The default is 53 columns x 4 versions x 4 conditions x 3 repeats = 2,544 short requests. A stopped run continues when you repeat the command. Results go to `runs/<model>/report.md`.

## Limits

- The tables are simple and tidy apart from the planted problems. Real tables are wider and messier.
- One subject area. A model's guesses about a fitness club say little about a ledger.
- The list of 48 meanings is mine. A real column can be something not on any list; "other" is offered, but a pick-list still makes the task easier than open description.
- "Settled by" labels are my judgement for the columns that aren't coin flips. Two columns are marked as judgement calls and reported separately.
- Four versions give four flips per coin-flip column. That's enough to see a model claim certainty it can't have, and too few to estimate its accuracy on any one column.
- Background on the method and on test data is in [`research/column-meaning-and-test-data.md`](../../research/column-meaning-and-test-data.md).
